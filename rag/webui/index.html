1

Read

Each file is loaded as plain text. Nothing clever: the text is the raw material for everything after.

2

Chunk

The text is split at blank lines and paragraphs are packed until the chunk size is reached. Each new chunk starts with the tail of the one before (overlap), so a sentence on a boundary keeps its context.

3

Embed

Each chunk becomes a list of numbers (a vector). Texts with similar content get similar vectors. Every tile below is one chunk's vector.

4

Store

The document, its chunks and their vectors go into SQLite. Vectors are float32 BLOBs; a trigger copies the text into the FTS5 keyword index.

B Ask a question

The question is embedded the same way, the nearest chunks are found, and they are handed to the LLM as context.

Nothing running.
5

Embed the question

The question goes through the same embedder as the chunks, so both live in the same space and can be compared.

6

Vector search

One SQL statement scores every chunk by cosine similarity to the question vector (1 = same direction, 0 = unrelated).

SELECT …, cosine_similarity(c.embedding, ?) AS score
FROM chunks c JOIN documents d ON d.id = c.document_id
ORDER BY score DESC LIMIT ?
7

Keyword search

The question's words are looked up in the FTS5 full-text index and ranked by BM25: rare matching words count for more.

SELECT …, -bm25(chunks_fts) AS score
FROM chunks_fts JOIN chunks c ON c.id = chunks_fts.rowid …
WHERE chunks_fts MATCH ? ORDER BY score DESC LIMIT ?
8

Fuse the two rankings

Cosine and BM25 scores cannot be compared, so only ranks are used: each list gives a chunk 1 / (60 + rank), rank counted from 0. Chunks high in both lists win.

9

Build the prompt

The kept chunks are numbered and pasted above the question, with an instruction to answer only from them and cite [n].

10

Generate

The LLM reads the prompt and writes the answer. With no LLM configured you see the context it would have been given.
